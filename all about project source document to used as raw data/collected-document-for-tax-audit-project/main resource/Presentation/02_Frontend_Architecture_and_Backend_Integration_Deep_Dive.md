## 1. Architectural Architecture & Component Tree

The ITAS Back-Office User Interface is built as a single-page application (SPA) optimized for high data density, audit regulatory compliance, and role segregation.

```
App.jsx
 └── AuthProvider (Keycloak / ITAS Principal Context)
      └── NotificationProvider (Live In-App Polling / Event Stream)
           └── AppRoutes
                ├── /ap/planning   ─── PlanningDashboard.jsx (Planning Team)
                ├── /ap/director   ─── DirectorDashboard.jsx (Audit Director)
                ├── /ap/regional   ─── RegionalDashboard.jsx (Regional Coordinators)
                ├── /ap/tax-center ─── TaxCenterDashboard.jsx (Branch Managers)
                ├── /ap/team-leader─── TeamLeaderDashboard.jsx (Team Leaders)
                ├── /ap/auditor    ─── AuditorDashboard.jsx (Field/Desk/TP Auditors)
                └── /tp/workspace  ─── TpAuditWorkspace.jsx (Transfer Pricing Lifecycle)
```

## 2. Persona Dashboards & Real-Time API Bindings

The frontend implements six primary persona interfaces tailored to each statutory role in the Ethiopian Ministry of Revenue:

### 2.1 Planning Officer Console (`PlanningDashboard.jsx`)
- **Location**: `src/features/ap/pages/planning/PlanningDashboard.jsx`
- **Primary Responsibilities**:
  1. Visualize national and regional risk distribution curves generated by the Risk Engine.
  2. Input annual plan targets, fiscal year, and revenue expectations.
  3. Pre-populate regional allocation matrices.
  4. Submit plan drafts for supervisory review.
- **Key UI Components & Buttons**:
  - `PreFilledQuotasButton`: Calls `GET /api/v1/backoffice/ap/plans/workflow/pre-filled-data`. Automatically populates regional table with suggested risk quotas.
  - `CreatePlanModal`: Multi-step modal for adjusting regional quota numbers per audit type (Desk, Field, Joint, TP, Comprehensive, Issue).
  - `SubmitToDirectorButton`: Initiates `POST /api/v1/backoffice/ap/plans/workflow/{planId}/submit-to-director`. Disables button, triggers loading spinner, shows success alert, and reloads plan status badge to `SUBMITTED_TO_DIRECTOR`.

### 2.2 Director of Audit Console (`DirectorDashboard.jsx`)
- **Location**: `src/features/ap/pages/director/DirectorDashboard.jsx`
- **Primary Responsibilities**:
  1. Executive overview of proposed national audit volumes against MoR revenue targets.
  2. Comparative analysis of regional allocations vs historical compliance yields.
  3. Executive sign-off, conditional amendment requests, or plan distribution.
- **Key UI Components & Buttons**:
  - `DirectorReviewCard`: Displays plan metadata, total proposed audits (e.g. 3,500), estimated revenue (e.g. 48.5B ETB).
  - `ApprovePlanButton`:
    - Opens formal decision modal.
    - Executes `planService.approveByDirector(planId, reason, actorId)`.
    - Updates local state optimistically, advances workflow status badge to `DIRECTOR_APPROVED`.
  - `RequestAmendmentsButton`:
    - Opens structured amendment drawer with regional feedback notes.
    - Executes `POST /api/v1/backoffice/ap/plans/{planId}/request-amendment`.
  - `DistributeToRegionsButton`:
    - Calls `POST /api/v1/backoffice/ap/plans/{planId}/submit-to-regional`.
    - Triggers cascade to the 7 regional coordinator workbenches.

### 2.3 Regional Coordinator Console (`RegionalDashboard.jsx`)
- **Location**: `src/features/ap/pages/regional/RegionalDashboard.jsx`
- **Primary Responsibilities**:
  1. Receive approved regional quotas (e.g. Addis Ababa: 700 cases).
  2. Sub-divide regional quotas across Branch Tax Centers (e.g. TC-AA-01, TC-AA-02, TC-AA-03).
  3. Solicit branch feedback and submit regional capacity counter-proposals.
- **Key UI Components & Buttons**:
  - `RegionalAllocationMatrix`: Interactive editable table displaying tax center allocations with automated row-level summation and variance validation (ensures branch totals match regional ceiling).
  - `SubmitSubAllocationsButton`:
    - Executes `planService.divideAllocations(planId, regionCode, tcAllocations, actorId)`.
    - Persists tax center distribution to `ap_plan_allocations`.

### 2.4 Tax Center Manager Console (`TaxCenterDashboard.jsx`)
- **Location**: `src/features/ap/pages/taxcenter/TaxCenterDashboard.jsx`
- **Primary Responsibilities**:
  1. Review branch-level allocated audit quotas.
  2. Evaluate local auditor staffing capacity.
  3. Submit adjustments or capacity justifications before final plan locking.
- **Key UI Components & Buttons**:
  - `TaxCenterFeedbackModal`: Multiline textarea for branch capacity feedback with number input for proposed quota adjustments.
  - `SubmitFeedbackButton`: Calls `PATCH /api/v1/backoffice/ap/plans/{planId}/allocations/{tcCode}/feedback`.

### 2.5 Team Leader Console (`TeamLeaderDashboard.jsx`)
- **Location**: `src/features/ap/pages/teamleader/TeamLeaderDashboard.jsx`
- **Primary Responsibilities**:
  1. Receive cascaded audit cases generated from the finalized plan.
  2. Inspect taxpayer risk profiles, sector, and revenue size.
  3. Assign lead senior/junior auditors.
- **Key UI Components & Buttons**:
  - `UnassignedCasesTable`: Real-time searchable and filterable table querying `GET /api/v1/backoffice/ap/cases?taxCenter={tcCode}&status=PENDING_ASSIGNMENT`.
  - `AssignAuditorModal`: Workload-aware dropdown showing each auditor's currently active case count.
  - `AssignCaseButton`:
    - Triggers `POST /api/v1/backoffice/ap/cases/{caseId}/assign-auditor`.
    - Updates case row status from `PENDING_ASSIGNMENT` to `ASSIGNED` with color transition.

## 3. Frontend Client Architecture & Service Layer

All backend HTTP communication is encapsulated in strongly typed modular services under `src/features/ap/services/`:

```
src/features/ap/services/
 ├── planService.js            ── Core API adapter for Plan workflow, creation, approvals, allocations
 ├── caseService.js            ── Adapter for Case queries, status transitions, and auditor assignments
 ├── notificationService.js    ── Real-time notification fetcher and mark-as-read handler
 ├── dataService.jsx           ── Aggregated caching and transformation service
 └── morIdentityAPI.js         ── User profiles, roles, and branch membership resolution
```

### 3.1 `planService.js` Implementation Highlights

The `PlanService` class encapsulates all HTTP communication, payload transformations, and caching:

```javascript
// Excerpt from src/features/ap/services/planService.js
class PlanService {
  /**
   * Transforms UI distribution state into backend regional allocation format
   * and executes POST to Spring Boot backend.
   */
  async createPlan(planData, actorId) {
    const regionIdToCode = {
      'federal_level': 'FED',
      'addis_ababa': 'AA',
      'amhara': 'BA',
      'oromia': 'BB',
      'dire_dawa': 'AB',
      'snnpr': 'CA',
      'somali': 'SO'
    };

    const regionalAllocations = Object.entries(planData.distribution || {}).map(([regionId, auditTypes]) => {
      const total = Object.values(auditTypes || {}).reduce((sum, count) => sum + (count || 0), 0);
      return {
        regionCode: regionIdToCode[regionId] || regionId.toUpperCase(),
        proposedCount: total
      };
    });

    const backendPayload = {
      planYear: parseInt(planData.year) || new Date().getFullYear(),
      planName: planData.name || 'Annual Audit Plan',
      regionalAllocations,
      distribution: planData.distribution,
      estimatedRevenue: parseFloat(planData.estimatedRevenue) || 10000000
    };

    const response = await fetch('/api/v1/backoffice/ap/plans/workflow', {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        'X-Actor-Id': actorId || 'planning-team-001'
      },
      body: JSON.stringify(backendPayload)
    });

    if (!response.ok) {
      const err = await response.text();
      throw new Error(`Plan creation failed: ${err}`);
    }

    return await response.json();
  }
}
export default new PlanService();
```

## 4. State Management, UI Reactivity & Error Handling

### 4.1 Asynchronous Lifecycle Pattern
Every interactive workflow action follows a strict 5-stage UI lifecycle:
1. **Initiation**: User clicks action button (e.g. "Submit Plan to Director").
2. **Optimistic Locking / Disable**: Button enters `loading={true}` state; spinner replaces icon to prevent duplicate clicks.
3. **HTTP Dispatch**: `fetch()` request dispatched with standard headers (`Content-Type`, `X-Actor-Id`).
4. **State Reconciliation**:
   - **On Success (HTTP 200/201)**: Toast notification is displayed (`type: 'success'`), target state is updated, and callback `onRefresh()` is triggered to pull the fresh state from `/full-state`.
   - **On Failure (HTTP 4xx/5xx)**: Loading state resets; error message is rendered inline or via toast (`type: 'error'`), highlighting exact server-side validation messages without breaking page layout.
5. **UI Re-render**: Active tab, phase stepper, or badge dynamically reflects the updated status.

### 4.2 Spacing, Responsiveness & Form Design
- **High-Density Data Grids**: Tables utilize fixed header pinning, sticky action columns, and monospace fonts for financial metrics (e.g. `ETB 278,562,000`).
- **Generous Textarea Padding**: Notes, justifications, and committee minutes are given spacious multi-line fields (`rows={4}`, `p-3`, `text-sm`, `rounded-xl`) with explicit placeholder guidance.
- **Color-Coded Status Tokens**:
  - `DRAFT` $\rightarrow$ Slate / Neutral
  - `SUBMITTED_TO_DIRECTOR` $\rightarrow$ Amber (Review Pending)
  - `DIRECTOR_APPROVED` / `FULLY_APPROVED` $\rightarrow$ Emerald (Authorized)
  - `AMENDMENT_REQUESTED` $\rightarrow$ Purple (Action Required)
  - `REJECTED` $\rightarrow$ Rose / Red (Halted)

## 5. End-to-End Component Interaction Sequence

```
User Action (Click "Approve Plan")
     │
     ▼
DirectorDashboard.jsx (UI State: loading = true)
     │
     ▼
planService.approveByDirector(planId, reason, actorId)
     │
     ├── HTTP POST /api/v1/backoffice/ap/plans/workflow/{planId}/approve-by-director
     │    └── Headers: X-Actor-Id: u-dir-audit
     │    └── Body: {"reason": "Targets verified against MoR budget"}
     │
     ▼
Backend Response (HTTP 200 OK with PlanResponse)
     │
     ▼
planService returns parsed DTO
     │
     ▼
DirectorDashboard.jsx reconciles state:
     ├── loading = false
     ├── setMsg({ type: 'success', text: 'Plan approved successfully!' })
     ├── setSelectedPlan(updatedPlan)
     └── onRefresh() triggers reload of dashboard metric cards
```
